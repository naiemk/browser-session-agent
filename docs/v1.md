# Browser Operations Agent — V1 (product)

## Outcome

A **non-developer** can sign in on the web, install a helper on Windows or Mac (no terminal, no Docker), and let our **hosted agent** drive a dedicated Playwright Chromium on their machine. They pay for the hosted agent. Logins stay in an isolated profile on their disk.

This is “option 2”: agent on our backend, Playwright packaged on the user’s PC, outbound control channel. Docker and the Pi CLI remain power-user paths, not onboarding.

The earlier multi-agent supervisor graph is **V2**, not V1.

## In scope

- Hosted web app: accounts, chat, live view, slash/command cards, billing hook
- Windows (`.msi` / `.exe`) and Mac (`.pkg` / `.dmg`) **Helper** that embeds Node + Playwright Chromium
- One-click **Connect this computer** — no token copy-paste (see pairing)
- Helper auto-starts at login, reconnects after sleep, keychain-stored device credential
- Same bounded tools and semantic inspect as the MVP (`BrowserSession` unchanged)
- Action harness: an act is accepted only after Playwright success + state delta / read-back
- Page plans: one model call writes a short branching script; a local interpreter talks to Playwright
- Batched fill as the degenerate (no-branch) form of a page plan
- Takeover lock: remote input only while `awaiting_takeover`
- Fail closed if the helper is quit or offline; chat still works
- Optional headed window on the desk; headless + live view is the default

## Out of scope (V1)

- Docker or terminal as the default install
- Driving the user’s daily Chrome (D2)
- A full Electron/Tauri “desktop app” product
- Cloud-hosted browsers as the default (optional later)
- CAPTCHA solvers, credential vaults, multi-agent supervisor graph
- Linux helper (power users keep Docker/CLI)

## Exit criteria

1. A new user creates an account, installs the helper with two clicks, and sees **Connected** without typing a token.
2. They start a goal in the web chat; the agent inspects and acts on the helper’s Chromium.
3. Login/CAPTCHA uses takeover + live view; after resume the agent continues from a fresh observation.
4. Quitting the helper makes browser tools fail with a clear “helper disconnected” message.

## Pairing (no token paste)

The user never sees `BSA_TOKEN`. The helper gets a **device credential** we issue after they click Allow.

```
Web (logged in)                         Helper (just installed)
      │                                        │
      │  1. Download Helper.msi / .pkg         │
      │  2. Install registers scheme bsa://    │
      │     and a login item                   │
      │                                        │
      │  3. Site redirects to                  │
      │     bsa://pair?code=<one-time>         │
      │───────────────────────────────────────►│
      │                                        │  4. POST /pair/exchange { code }
      │◄───────────────────────────────────────│
      │  5. device_token + expires             │
      │                                        │  6. Store in Credential Manager /
      │                                        │     Keychain; delete the code
      │  7. WSS /node with device_token        │
      │◄───────────────────────────────────────│
      │  UI shows Connected                    │
```

Fallback if the custom scheme fails (corporate Mac, browser block):

- Helper listens on `127.0.0.1` and opens the already-logged-in site with a `challenge`
- User clicks **Allow this computer**
- Site POSTs the credential to localhost, or the helper polls `/pair/claim`

One-time codes expire in minutes and bind to the signed-in account. The device token is rotatable and revocable from the web “This computer” page. Do not put long-lived secrets in the installer binary (a copied `.exe` must not steal someone else’s session).

## Action harness (do not trust the model’s story)

The model may claim it clicked Submit when the tool never ran, or when Playwright clicked a dead control and the page did not change. **The harness is the source of truth.** An action is *accepted* only after Playwright reports success **and** page state actually changed in the expected way. Chat UI should render harness results, not the assistant’s prose, as what happened.

This is a stricter form of today’s optional `expect` (already in `BrowserSession.act`). V1 makes a postcondition **required**, with defaults per action so the model cannot skip it.

```
LLM proposes: click e3
        │
        ▼
Harness
  1. Ref e3 still exists (re-tag immediately before the gesture)
  2. Playwright click() does not throw
  3. Read-back: for type/select, control.value matches
  4. State delta: URL, dialog, control values, or snapshot diff changed
     OR an explicit expect (urlIncludes / textVisible / …) passed
        │
        ├── accepted → tool result { ok, observation, verification: passed }
        └── rejected → tool result { ok: false, recovery } — model must not
                       narrate success; it only sees the rejection
```

Default postconditions (when the model omits `expect`):

| Action | Accepted if |
| --- | --- |
| `type` / `select` | Read-back value equals what we sent |
| `navigate` | URL matches the target (allow redirects that still contain the host/path intent) |
| `click` | Snapshot diff is non-empty **or** URL/title/dialog changed within a short wait |
| `scroll` / `wait` | Wait condition met; scroll is accepted if Playwright succeeded |

A click that throws, hits a missing ref, or produces **no** delta is `noop` / `failed`, never `ok`. That stops the “I submitted the application” hallucination after a no-op click.

Prose in the transcript is not evidence. Only harness-accepted tool results are.

## How the agent talks to Playwright

The model does **not** steer by watching the JPEG stream. JPEGs are for **humans** (live view / takeover).

The agent calls the same tools as the CLI. Each `browser_inspect` returns a compact **semantic snapshot**:

- URL, title, tab id
- Interactive controls with stable-for-this-snapshot refs (`e1`, `e2`, …) plus role, name, tag
- Dialogs, page/console errors, a short diff vs the last snapshot

Then it acts with **refs**, not CSS or screenshots: `browser_click { ref: "e3" }`, `browser_type { ref: "e1", text: "…" }`. After each action the harness re-inspects and applies a required postcondition (see above). Failures write a recovery note from that new observation.

Playwright already provides this abstract state — we do not need to invent a second vision stack for V1. Optional later: attach a screenshot to the tool result **on failed expect** only (we already store those on disk).

```
LLM  ──inspect──►  Observation JSON (refs)
     ──click e3──►  Playwright
     ──inspect──►  new Observation + expect
Human ──JPEG────►  live view (takeover input only if awaiting_takeover)
```

### Why one click feels slow — and how to speed it up

Playwright is not the bottleneck. A click+inspect is usually **under a second**. The 2–15s number is **one LLM turn per gesture**. Five fields + submit can be six model calls.

V1 speed rules:

1. **Every accepted `act` already returns a fresh observation.** Do not spend a whole turn on `browser_inspect` after a click.
2. **Batch mechanical steps in one tool.** Example: `browser_fill` `{ fields: [{ref, text}], submit?: ref, expect }`. The harness runs type/type/click locally, checks each read-back, and returns one result. One LLM call for a whole login form.
3. **Cheap model for fill-and-click** once the snapshot is clean (`@low` / `@medium`); `@high` / `@ultra` for first inspect and recovery (D12).
4. **Keep snapshots small.** Truncate noisy lists; keep editors and primary actions.
5. **No screenshot on success.** JPEG stays on the human live view.
6. **Harness confirms the gesture** — do not wait for another LLM call to decide if the click “counted.”

Target for a form-heavy apply step: **one model call + a few hundred ms of Playwright**, not one model call per keystroke.

Twitchy UI → takeover. No pixel-click API and no vision-as-primary in V1. Refs stay the contract (D5). Path programs target controls by accessible name, not only snapshot refs, because refs go stale as soon as a dropdown opens.

## Page context and path programs

One LLM call per gesture is the wrong grain. A person looking at an apply form does not think “click e12.” They think: *this is a Greenhouse form; I need work auth, country, resume; country is a searchable combobox; try United States, then USA, then scroll.* That is a **page context** plus a **path program** — a few predicted futures, not a live video loop and not unrestricted Playwright (D2).

`browser_fill` is the no-branch special case (type these fields, then submit). Comboboxes, typeaheads, and “if this label else that label” need an explicit try-list. The model writes that script **once**. A local interpreter runs it against Playwright, streams progress, and returns actuals. The model is invoked again only when the page context changes or every predicted path fails.

```
LLM  (once per page)     writes PagePlan JSON
        │
        ▼
Interpreter              closed verbs only
  for each action
    setup (open the field)
    for each attempt in order
      steps → harness → re-inspect
      if successWhen → optional then (select the option)
      if doneWhen / then ok → next action
    if all attempts miss → escalate with actuals
        │
        ▼
Chat                     progress + actuals (not model prose)
```

### What the model decides

On first inspect of a stable page it writes:

1. **Context** — what this page is, plus an optional URL/title hint so we notice if we navigated away.
2. **Overall actions** — the jobs, in order (`select_country`, `attach_resume`, `submit`).
3. **For each action, the next actions if successful** — an ordered `try` list. First attempt that the harness accepts wins.

It does **not** author `page.click`, CSS, or a site-wide state machine. The DSL is a closed set of the same verbs we already have (`click`, `type`, `select`, `scroll`, `wait`) plus predicates (`option_visible`, `value_includes`, …) and two structured ops: `scroll_until` (bounded) and `click_first` (first visible of a label list).

### Country dropdown (the motivating script)

```
action select_country
  setup: click label "Country"
  try type_united_states
    type "United States"
    if option_visible "United States"
      click that option
      done when country value includes "United"
  try type_usa
    clear, type "USA"
    if option_visible "USA"
      click it
      done when value includes "USA"
  try scroll_known_labels
    clear
    scroll_until any of
      "United States of America" | "United States" | "USA"
    click_first of those labels
    done when value includes "United" or "USA"
  else escalate — here is what we actually saw
```

That JSON lives in `src/plan/examples.ts` (`selectCountryUnitedStates`). The interpreter in `src/plan/interpret.ts` runs it; unit tests drive a fake combobox through all three branches.

`successWhen` is the **gate** (“the option appeared”), not the final truth. After the list closes, “United States” is no longer visible — `doneWhen` is the read-back. If `then` is omitted, `successWhen` is the final check.

### Why targets are names, not only `e12`

A snapshot ref is valid until the next inspect. Opening a listbox rewrites the DOM; `e12` is often gone. The script addresses **Country** by label / role+name / visible text. The interpreter re-resolves after every step. Refs are still allowed for a single gesture on the current snapshot; they are the wrong default inside a multi-step attempt.

### When the LLM is called again

| Event | Next step |
| --- | --- |
| Plan completed | New context for the next page (or stop) |
| Hint miss (URL/title changed) | Escalate — we left the page |
| Every attempt failed | Escalate with actuals + last observation |
| Harness `awaiting_takeover` | Human; resume starts a new inspect → new plan |
| Unexpected dialog / error | Escalate |

Not an event: “I finished a click.” That is interpreter progress.

### What chat shows

Stream `ProgressEvent`s: *trying United States… option not in list; trying USA… selected USA.* The tool result is `{ status, actuals, completedActionIds }`. Same rule as the harness: the assistant must not narrate a success the interpreter did not accept.

### Bounds (keep the script small)

| Limit | Cap |
| --- | --- |
| Actions per plan | 8 |
| Attempts per action | 6 |
| Steps per attempt | 12 |
| `scroll_until` loops | 8 |
| Predicate nesting | 4 |
| Wait | 15s |

Predict two to four futures, then re-plan. A 50-step site FSM will be wrong and unreadable. No `evaluate`, no CSS, no arbitrary JS — that is BetterWright, which we rejected (D2).

### Wiring (implementation order)

1. Types + validator + interpreter — done (`src/plan/`).
2. `PlanRuntime` over `BrowserSession.act` + inspect (name → current ref, then existing harness).
3. Tool `browser_run_plan` { plan }. The cheap model writes the plan; the interpreter runs it on the helper.
4. Chat cards for progress/actuals.
5. Treat `browser_fill` as syntactic sugar for a plan with one attempt per field.

Do not add a second routing layer (D12). Do not steer the script from JPEGs (D16). Each interpreter step still goes through the harness (D17).

## Packaging (Windows / Mac)

CI builds the helper (not only the Docker image):

- Windows: signed installer that places the node agent, Playwright Chromium, and registers `bsa://` + Run at login
- Mac: signed + notarized pkg/dmg, same, plus LaunchAgent

Double-click install. No terminal. No Docker. Profile at `%APPDATA%\browser-session-agent` / `~/Library/Application Support/browser-session-agent`.

Docker and `scripts/run-desktop-node.sh` stay for operators who want them (D14). They are not the consumer path.
